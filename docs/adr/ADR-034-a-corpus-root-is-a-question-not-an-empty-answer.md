# ADR-034: Let `adr-next` answer for a corpus root instead of reporting it empty

**Status:** Accepted
**Date:** 2026-09-04
**Owner:** zy
**Spec:** None — no spec stage
**Cross-references:** docs/adr/ADR-005-a-gate-reports-what-it-observed.md, plugin/scripts/work-next.mjs, docs/BACKLOG.md
**Governs:** plugin/bin/adr-next
**Enforced-by:** `next: a corpus root is enumerated, not reported empty`, `next: a corpus with nothing ready is not a corpus with ready work`, `next: a record folder is not a corpus of one`, `next: a corpus names an undecided record before offering its tasks`, `next: an unreadable record is could-not-look, not a record holding nothing`, `next: nothing ready is a verdict only when everything was read`, `next: a status that could not be read is unknown, never decided`, `next: a symlinked record's owner sits beside the link, not beside its target`
**Invalidates:** none — checked. ADR-005 governs the vocabulary a gate may use for an observation it did not make, and this record applies it rather than changing it.
**Served-path change:** `adr-next <corpus root>` answered `no task files` and now enumerates the records it holds. An adopter who addressed the corpus at its natural granularity got a confident wrong answer; they now get the answer they asked for.

## Context

**GitHub issue #10, filed 2026-09-04** against 2.60.0, measured on a corpus of 37 records.
`adr-next docs/adr --all` printed:

    adr-next: no task files in docs\adr

That is the same sentence an empty `tasks/` directory gets. The corpus had six ready tasks, and the
session-start banner — generated by `plugin/scripts/work-next.mjs`, walking the same tree — listed
them in the same session. So the plugin contradicted itself, and the half that was wrong was the one
the documentation tells people to trust.

**The mechanism, confirmed in source.** `resolve_tasks_dir` (`plugin/bin/adr-next:410`) falls back to
returning the directory it was given when that directory holds no `tasks/` child. A corpus root
therefore arrives at the single-record path as though it were a tasks directory, `load()` finds no
task files in it, and its emptiness is reported as the ANSWER rather than as a scope mismatch.

**What did not reproduce, and is recorded as unreproduced rather than refuted.** The reporter also
measured **exit 0**, which would make the output indistinguishable from a clean corpus. That branch
is `return 1` (`plugin/bin/adr-next:574`), and exit 1 is what this machine gives at HEAD *and* at the
reporter's own v2.60.0, checked out and run. Their invocation went through a `~/.claude/bin`
forwarder under Windows Git Bash, which cannot be driven from here; the `.cmd` shim propagates status
correctly and carries a comment recording the 2026-08-30 defect where it did not. The confound is
named because it may matter and nobody here can remove it.

**The message defect alone is sufficient.** `no task files` over a corpus with ready work is a gate
reporting an observation it did not make — ADR-005's rule, applied to scope rather than to a failed
subprocess. A filter that matched nothing is "I could not look", not "the thing is absent".

## Existing Primitives Audit

- **`plugin/scripts/work-next.mjs`** — already walks a corpus root and groups ready tasks by record;
  it is what the session-start banner prints. It answers a broader lifecycle question ("which stage
  is waiting"), is Node rather than Python, and is not what the documentation points at for "which
  task is ready". It proves the enumeration is possible; it does not make `adr-next` correct.
- **`adr-next` itself** — `resolve_tasks_dir` already accepts three shapes (the tasks directory, the
  record folder, the record file) precisely because a tool that knows what you meant and refuses to
  say so is one people stop typing. A corpus root is the fourth shape, and the same argument covers
  it.
- **`adr-lint`, `adr-debt`** — both take a corpus root already, so the shape is not foreign to the
  gates; `adr-next` is the outlier.
- **`adr-state.mjs` / `adr-context.mjs`** — corpus-wide, but answer about governance and supersession,
  not readiness.

Nothing existing covers it.

## Decision

**`adr-next` detects a corpus root and enumerates it, grouped by record.**

A path is treated as a corpus root when all three hold: it has no `tasks/` child of its own
(`resolve_tasks_dir(target) == target`), it owns no task files directly, and at least one non-hidden
child resolves to a tasks directory through the existing `resolve_tasks_dir`. Detection, not a new
flag — the reporter's complaint is precisely that they had to know which granularity the tool wanted.

**Dot-prefixed directories are excluded**, because `.git` is not a record. This is stated because an
earlier draft of this section described a detector the code did not implement, and a record that
claims a rule it does not follow is worse than one that admits a limit.

**A record this tool cannot READ is not a record holding nothing.** An unreadable child is collected
separately, named on stderr, and withheld from the "nothing is ready" verdict: exit is 1 there, not
3, because that claim requires having looked everywhere. A ready task found elsewhere still exits 0,
since that is a positive claim about work that exists and stays true whatever the unread record
holds. `Path.glob` swallows `OSError` and yields nothing, so this needs an explicit `iterdir()`
probe — without it an unreadable record is indistinguishable from an empty one.

**Status is resolved from the path the caller reached the record by**, not from the resolved one: a
symlinked record's file sits beside the LINK, and `.resolve()` sent the lookup to the link's target.
`undecided` is three-state — `null` when the status could not be read at all, because reporting that
as `false` tells a machine caller the record is Accepted when nothing was read.

**The exit-code contract is preserved exactly**, because it is the part callers branch on:

| exit | single record | corpus root |
|---|---|---|
| 0 | a task is ready | some record has a ready task |
| 3 | nothing ready | no record has a ready task |
| 1 | could not answer | could not answer |

A directory holding neither records nor task files stays exit 1 with a message naming what it failed
to find. That case ALREADY behaved correctly before this record, and its test passed on first run —
recorded here because a record that claimed to fix it would be taking credit for behaviour it did not
change.

`--json` grows a `records` object keyed by record directory, each holding the same
`ready`/`done`/`blocked`/`stopped` shape a single record returns. The single-record JSON shape is
unchanged, so existing callers keep parsing.

## Alternatives Considered

- **Exit non-zero naming the mistake** (`docs/adr is a corpus root; try adr-next docs/adr/ADR-001-…`).
  Issue #10's first proposal, and the smallest thing that removes the ambiguity. Rejected as the
  final answer because it teaches the caller to do by hand what the tool can do, and the tool already
  bends to three input shapes for exactly that reason. It is strictly better than today and strictly
  worse than enumerating.
- **Distinguish the three states by message only**, changing no capability. Rejected for the same
  reason, and it leaves the documented workflow — "ask which task is ready rather than reading the
  task files" — unusable at the granularity people actually type.
- **A `--corpus` flag.** Rejected: a caller who knew to pass it would already have known to address
  one record. A flag here is a way of blaming the user for the tool's scope.
- **Delegate to `work-next.mjs`.** Rejected: it answers a different question, it is Node rather than
  Python, and a gate that shells out to another runtime to answer its own question acquires that
  runtime's failure modes for no gain.

## Consequences

The call the documentation recommends now works at the granularity people type it at. `adr-next` and
`adr-lint` accept the same shapes, so "point it at the corpus" is true of both.

**A corpus of many records prints many lines.** The single-record default form (no `--all`) still
names one next task; the corpus form is grouped and reports per record. On a large corpus this is a
longer answer than before, and that is the answer being asked for.

The reported exit-0 behaviour is NOT fixed by this record, because it was never reproduced. If it is
real it lives below this code — in the forwarder, the shim, or the Windows spawn — and it would now
be less harmful (the message no longer reads as a clean corpus) without being addressed. The issue
should stay open on that half until someone on Windows can measure it.

## Wiring & Contract Changes

`adr-next` gains a corpus branch ahead of the single-record path; the single-record path is unchanged
and its JSON shape is unchanged. The classification loop is extracted so both paths use one copy —
two copies of a readiness rule is how `Consumes` came to be missing the foreign-pointer rule
(BACKLOG §41).

## Out of Scope

- The unreproduced exit-0 report from Windows Git Bash (deferred: needs a measurement nobody here can
  take; the issue was closed on the reproduced half, asking the reporter to reopen with
  `adr-next --version` if 2.64.0 still shows it).
- `adr-next` recursing more than one level into nested corpora (deferred: no reported need, and a
  depth rule nobody has asked for is speculative complexity).
