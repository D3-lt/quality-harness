## The command

```

**Why:** Both new tests live in the package, so a whole-suite run is the only single command that proves `ResolveCitations` works *and* that it didn't cost you any of the large existing suite — and `-count=1` defeats the test cache so the exit code reflects this checkout rather than a prior one.

## The trap to avoid

Don't scope the fence with `-run`:

```sh
go test ./... -run TestResolveCitations   # ✗
```

`go test` exits **0** when a `-run` regex matches nothing — it prints `testing: warning: no tests to run` and passes. So a typo in the test name, a file left behind a build tag, or a deleted test file all give you a green fence. It also drops the regression half of the check entirely.

Note also that `TestResolveCitations_CanFail` is a normal passing test: it asserts that the checker *reports* an unresolved citation. It needs no inverted exit code or special handling — it's green inside the same run, and it's what keeps `TestResolveCitations` from being satisfiable by a `ResolveCitations` that resolves everything unconditionally.

## If you want the fence tamper-evident

The one real hole above is that the suite stays green if the new tests stop existing or start skipping. If the fence has to survive that:

```sh
go test ./... -count=1 && \
go test ./... -count=1 -v -run '^TestResolveCitations(_CanFail)?$' 2>&1 \
  | grep -c '^--- PASS: TestResolveCitations' | grep -qx 2
```

First clause is the real fence; second asserts exactly those two tests ran and passed. I'd only reach for this if the fence is enforced by CI against future diffs rather than checked once against yours.
